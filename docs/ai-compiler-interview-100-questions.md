## 3. C++ 与工程基础

### 1. 左值、右值、右值引用分别是什么？

左值通常有持久身份，可以取地址；右值通常是临时值。右值引用 `T&&` 让我们能够区分“可被搬走的对象”，从而触发移动语义。AI 编译器工程里大量 IR 节点、字符串、容器拼装都依赖这套机制减少拷贝。

### 2. `std::move` 做了什么？

`std::move` 本身不移动对象，它只是把一个表达式显式转换成右值，从而让后续代码有机会调用移动构造或移动赋值。真正的资源转移发生在目标类型的 move 操作里。

### 3. 移动构造和拷贝构造有什么区别？

拷贝构造通常复制资源，源对象和目标对象都保留有效资源；移动构造则把源对象的资源所有权转给目标对象，源对象进入“可析构但值未指定”的状态。对于大 `vector`、字符串、IR 容器，移动通常明显更便宜。

### 4. 什么是 RAII？为什么在编译器项目里重要？

RAII 是“资源获取即初始化”，即把资源生命周期绑定到对象生命周期。这样栈展开时会自动析构并释放内存、文件句柄、锁。编译器工具链里经常要管理临时 buffer、文件、计时器、上下文对象，RAII 可以显著减少泄漏和异常路径 bug。

### 5. `unique_ptr`、`shared_ptr`、`weak_ptr` 的区别是什么？

`unique_ptr` 独占所有权，开销最小，最适合树状或明确归属的对象；`shared_ptr` 引用计数共享所有权；`weak_ptr` 用来打破循环引用或做非拥有观察。编译器 IR 节点如果生命周期明确，优先考虑值语义、arena 或 `unique_ptr`，不要默认全用 `shared_ptr`。

### 6. `vector` 扩容时发生什么？

`vector` 扩容会分配更大的连续内存，把旧元素拷贝或移动到新内存，再释放旧内存。若元素很大且 move 不高效，扩容代价会很高，所以要善用 `reserve()`，并尽量让类型支持高效移动构造。

### 7. `emplace_back` 和 `push_back` 的区别是什么？

`push_back` 需要一个现成对象；`emplace_back` 接收构造参数并在尾部原地构造对象。若本来就有对象，两者差别不一定大；若直接传构造参数，`emplace_back` 通常更自然，也可能少一次临时对象构造。

### 8. `unordered_map` 和 `map` 的区别是什么？

`unordered_map` 基于哈希表，平均查找复杂度是 `O(1)`；`map` 基于红黑树，查找复杂度是 `O(log n)`，并保持有序。LRU、符号表缓存、IR lookup 常用 `unordered_map`；需要顺序遍历或范围查询时更适合 `map`。

### 9. `++it` 和 `it++` 有什么区别？为什么遍历时常写 `++it`？

`++it` 是前置自增，先加再返回；`it++` 是后置自增，先保存旧值再加。对迭代器来说后置版本理论上可能多一个临时对象，因此 STL 风格更推荐 `++it`。

### 10. 编译器项目里常见的内存管理策略有哪些？

常见策略包括值语义、`unique_ptr`、对象池、arena allocator、bump allocator。IR 节点数量大、生命周期集中释放时，arena 非常常见，因为它能减少碎片和 malloc/free 开销。

实践步骤：

1. 写一个包含大 `vector<int>` 成员的结构体。
2. 分别测试没有 move、默认 move、手写 move 的拷贝/扩容耗时。
3. 再分别对 `vector<T>` 使用 `reserve()` 和不使用 `reserve()` 做 benchmark。
4. 观察对象构造、移动、析构次数。

## 4. 编译原理基础

### 11. 编译器通常分哪几个阶段？

典型流程是前端、IR、中端优化、后端代码生成和运行时支持。AI 编译器常把“图导入 / 图优化 / kernel 生成 / runtime 执行”映射到这条链路上。

### 12. 什么是 IR？为什么编译器需要 IR？

IR 是中间表示，用来隔离前端语言和后端硬件细节。它既要足够抽象以承载优化，也要足够精确以支持 lowering 和 codegen。AI 编译器里常见多层 IR：图级 IR、算子级 IR、循环级 IR、目标后端 IR。

### 13. 什么是 SSA？为什么 SSA 常见？

SSA 要求每个变量只被定义一次，若控制流汇合会插入 `phi`。这样 def-use 关系更清晰，很多优化和数据流分析都更简单，例如常量传播、死代码删除、值编号。

### 14. CFG 是什么？为什么重要？

CFG 是控制流图，节点通常是基本块，边表示控制转移关系。很多传统编译分析如支配关系、活跃变量、循环识别、LICM 都基于 CFG。

### 15. 什么是基本块？

基本块是只有一个入口、一个出口的直线代码片段，中间没有分支跳转进入或离开。它是很多优化和指令调度的基本单位。

### 16. DCE 是什么？怎么做？

DCE 是死代码删除，删除对程序结果无影响的语句或节点。常见做法是从有副作用或最终输出反向做可达性/活跃性分析，未被使用的定义就可以删掉。

### 17. Constant Folding 是什么？

常量折叠是在编译期把常量表达式直接算出结果，例如 `2 + 3` 变成 `5`。在 AI 图里典型场景是 shape 计算、常量广播、某些只依赖常量输入的算子。

### 18. CSE 是什么？

CSE 是公共子表达式消除，若两个表达式操作数和操作相同，而且中间没有破坏语义的副作用，就可以复用已有结果而不是重复计算。

### 19. 常见循环优化有哪些？

常见包括 loop unroll、tiling、fusion、interchange、vectorization、software pipelining、LICM。AI 编译器里最关键的通常是 tiling、fusion、vectorization，因为它们直接影响访存局部性和并行度。

### 20. LICM 是什么？

LICM 是循环不变代码外提，把循环中每次迭代都一样的计算移到循环外。这样可减少重复开销，也为后续优化创造更干净的循环体。

实践步骤：

1. 选一个简单矩阵加法或卷积伪代码。
2. 手动画出 CFG 和基本块。
3. 标出每个变量的定义点和使用点。
4. 人工判断哪些语句能做常量折叠、DCE、LICM。
5. 再尝试用 MLIR/LLVM 工具观察真实 pass 前后的 IR。

## 5. LLVM / MLIR 基础

### 21. LLVM IR 和 MLIR 的定位有什么区别？

LLVM IR 更接近传统低层编译和目标代码生成；MLIR 更适合表达多层抽象，从张量、线性代数、循环到 LLVM dialect 都能统一在一个框架里。AI 编译器通常用 MLIR 做高层到中层，再逐步 lowering 到 LLVM IR 或别的后端。

### 22. MLIR 的 `Dialect` 是什么？

`Dialect` 是一组操作、类型、属性和规则的命名空间，用来表达某个领域抽象。比如 `arith`、`scf`、`linalg`、`tensor`、`memref` 都是不同层次的领域语言。

### 23. `Operation`、`Region`、`Block` 分别是什么？

`Operation` 是 MLIR 的核心单位，表示一条操作；`Region` 是操作内部承载控制流或嵌套结构的容器；`Block` 是 region 中的一串操作序列。理解这三个概念是读懂 MLIR IR 和写 pass 的基础。

### 24. `tensor` 和 `memref` 的区别是什么？

`tensor` 更偏值语义，常用于高层张量计算；`memref` 更偏存储视角，描述内存布局、shape、stride 和地址空间。很多 lowering 会从 `tensor` 逐步转向 `memref`，以便进入 bufferization 和更低层代码生成。

### 25. 什么是 ODS？

ODS 是 Operation Definition Specification，用 TableGen 方式统一定义 op 的名字、参数、结果、属性、校验和接口。它减少样板代码，也让 op 的声明更集中、更可维护。

### 26. PatternRewrite 是什么？

PatternRewrite 是 MLIR 里基于匹配-重写的变换机制，用于 canonicalization、融合、lowering 等场景。你写一个 pattern 匹配某类 op 组合，再生成新的 op 替换旧结构。

### 27. Canonicalization 是什么？

Canonicalization 是把 IR 变成更规范、更适合后续优化的一组等价变换。例如去掉冗余 reshape、合并常量表达式、统一某些操作形式。它不一定直接提速，但能让后续 pass 更容易命中。

### 28. 什么是 bufferization？

bufferization 是把张量值语义逐步转换成显式内存对象的过程。它要处理别名、原地更新是否合法、临时 buffer 如何分配等问题，是高层 IR 走向后端的重要桥梁。

### 29. MLIR pass 一般怎么组织？

通常按层级组织：图规范化、高层融合、张量到循环、循环到内存、目标相关 lowering。每个 pass 尽量职责单一，pass pipeline 则负责整体顺序和阶段边界。

### 30. 什么时候应该写自定义 dialect？

当现有 dialect 无法自然表达你的领域语义，或者你需要保留某些高层信息供后续优化使用时，可以写自定义 dialect。若只是做小范围变换或实验，优先复用现有 dialect 往往更划算。

实践步骤：

1. 用 `mlir-opt` 跑一个 `linalg` 示例。
2. 观察从 `tensor` 到 `memref` 或 `scf/affine` 的 IR 变化。
3. 写一个最小 pattern，把 `add(x, 0)` 规约成 `x`。
4. 再写一个最小 pass，把 pattern 注册进 pipeline。

## 6. GPU / CUDA / Triton 基础

### 31. GPU 为什么适合深度学习算子？

GPU 有大量并行计算单元和高带宽内存系统，适合大规模同构数据并行。矩阵乘、卷积、归约这类规则计算非常容易映射成大量线程同时执行。

### 32. `thread`、`block`、`grid` 是什么关系？

线程是最小执行单元；多个线程组成 block；多个 block 组成 grid。block 内线程可以用共享内存和同步原语协作，而跨 block 协作通常要借助更高层调度或多阶段 kernel。

### 33. 什么是 warp？

warp 是 GPU 上一组同步调度的线程集合，NVIDIA 常见是 32 个线程。若一个 warp 内控制流分叉，硬件通常要串行执行不同分支，从而降低效率。

### 34. shared memory 的作用是什么？

shared memory 是 block 内线程共享的低延迟片上存储，适合缓存重复访问的数据、做 tile 重用和线程协作。典型场景是 GEMM、卷积、归约。

### 35. 什么是 memory coalescing？

当一个 warp 中线程访问连续且对齐的地址时，硬件可以合并成更少的全局内存事务，这就叫 coalescing。若访问模式离散、步长奇怪，就会浪费带宽。

### 36. 什么是 bank conflict？

shared memory 会被划分成多个 bank。如果同一个 warp 的多个线程同时访问同一 bank 中不同地址，就会发生 bank conflict，导致访问串行化。

### 37. occupancy 是什么？

occupancy 是一个 SM 上活跃 warp 数量相对理论上限的比例。它不是越高越好，但过低往往说明无法很好隐藏访存或流水线延迟。

### 38. Triton 的编程模型有什么特点？

Triton 用 Python 写 kernel，但表达的是块级并行和显式内存访问模式。它比 CUDA 更偏张量块抽象，常用于快速编写 GEMM、LayerNorm、Softmax、Attention 等 kernel。

### 39. Triton kernel 的性能通常受哪些因素影响？

核心因素包括 tile 大小、寄存器压力、shared memory 使用、向量化加载、mask 开销、访存是否合并、流水线深度以及 block 数量能否填满 GPU。

### 40. Triton 和 CUDA 应该怎么取舍？

如果目标是快速验证高性能算子、提升研发速度，Triton 通常很合适；若需要极致控制、复杂同步、特殊硬件特性或更底层优化，CUDA 往往更灵活。很多团队会混用：核心热算子保留 CUDA，迭代频繁算子用 Triton。

实践步骤：

1. 先写一个最朴素的 CUDA 或 Triton 向量加法。
2. 再实现一个 tiled GEMM。
3. 用 profiler 观察 global load/store、occupancy、shared memory 使用。
4. 改 tile 参数并对比吞吐变化。

## 7. AI 图编译与 IR 优化

### 41. AI 编译器里的图级 IR 一般承担什么职责？

图级 IR 主要表达模型结构、算子依赖、shape、dtype、常量、布局和一些高层语义。它适合做融合、常量折叠、算子替换、布局传播和后端切分。

### 42. 为什么 AI 编译器常用多层 IR？

因为“一个 IR 同时兼顾模型语义、优化便利性和硬件细节”通常很难。多层 IR 可以逐步丢失高层信息，把问题拆成更适合各阶段处理的表示。

### 43. 算子融合为什么能提速？

融合能减少 kernel launch 次数、减少中间张量写回全局内存、提升 cache 命中和数据重用。比如 `linear + relu`、`matmul + bias + gelu` 都是典型融合场景。

### 44. 算子融合什么时候可能变差？

过度融合可能导致寄存器压力过高、代码体积变大、并行粒度下降、调度更困难，甚至破坏原本高效的库调用。融合必须结合硬件资源和算子特征权衡。

### 45. 图编译中的 shape inference 是什么？

shape inference 是根据输入 shape、算子规则和属性，推导每个中间张量的 shape。它是很多优化的前提，因为融合、内存规划、布局选择都依赖 shape 信息。

### 46. 常量传播在神经网络图里常见在哪些地方？

常见于 shape 计算子图、某些参数折叠、固定掩码、静态广播、固定索引和编译期能算出的派生参数。若模型图里混有控制流，也可能对分支条件和边界值有帮助。

### 47. 图分区 / 后端切分是什么意思？

当同一张模型图中有的算子适合 GPU，有的适合 NPU/CPU，或者不同后端支持集不同，就要把图切成多个子图分别下发给不同后端执行。这一步通常会引入跨设备数据拷贝和调度边界。

### 48. 为什么需要 legality check？

因为不是所有看起来“可融合 / 可 lower”的结构都真的满足语义和硬件约束。legality check 要验证 dtype、shape、布局、副作用、精度要求和目标后端支持性。

### 49. ONNX / FX / TorchDynamo 在图编译里分别扮演什么角色？

ONNX 更像通用交换格式；FX 是 PyTorch 的 Python 层图表示工具；TorchDynamo 则负责在运行时抓取 Python 程序并导出更稳定的图。很多编译器会从其中之一接图，再进入自己的 IR 管线。

### 50. 图级优化和 kernel 级优化有什么边界？

图级优化关心跨算子结构、全局依赖和算子组合；kernel 级优化关心单个或少数融合算子的循环、访存、线程布局。两者相互影响，但分析粒度和目标不同。

实践步骤：

1. 选一个小 MLP 或单层 attention 的 FX 图。
2. 打印节点依赖、shape 和常量。
3. 手工实现一次 `linear + relu` 融合。
4. 对比融合前后的节点数、内存写回次数和执行时间。

## 8. 量化、布局与内存优化

### 51. PTQ 和 QAT 有什么区别？

PTQ 是训练后量化，不改训练过程，部署成本低；QAT 是量化感知训练，在训练中模拟量化误差，通常精度更稳。编译器侧既可能支持 PTQ 图变换，也可能承接 QAT 导出的量化图。

### 52. 对称量化和非对称量化的区别是什么？

对称量化通常以 0 为中心，只用 scale；非对称量化会引入 zero-point，更灵活地覆盖非对称分布。硬件实现和精度需求会影响选择。

### 53. per-tensor 和 per-channel 量化怎么选？

per-tensor 简单、开销低，但精度可能差；per-channel 尤其适合卷积或线性层权重，因为不同通道统计差异较大，通常精度更好。

### 54. 为什么布局会影响性能？

布局决定数据在内存中的排列方式，直接影响向量化、连续访问、cache 命中和后端库调用匹配情况。典型例子是 `NCHW`、`NHWC`、`blocked layout` 在不同硬件上的差异。

### 55. 什么是 layout propagation？

layout propagation 是在图中传播并选择布局，尽量减少不必要的 transpose/reorder。理想情况是让一段子图在同一种高效布局里连续执行。

### 56. 内存规划在 AI 编译器里做什么？

内存规划负责决定中间张量何时分配、何时释放、能否复用同一块 buffer。它直接影响峰值显存/内存占用，也是大模型推理优化的重要部分。

### 57. buffer reuse 的核心条件是什么？

核心条件是生命周期不重叠，且 dtype、shape、对齐和别名约束允许复用。若有异步执行或跨流并发，还要额外考虑同步关系。

### 58. inplace update 为什么难？

原地更新能省内存，但容易破坏值语义、梯度依赖、别名关系和后续复用分析。编译器必须证明写回不会影响仍需要旧值的路径。

### 59. 激活检查点和内存优化有什么关系？

激活检查点通过“少存中间值，后面需要时重算”换取更低显存。它本质上是算力和内存之间的 tradeoff，在训练图编译和调度里很常见。

### 60. 量化后为什么还需要重新做融合和 codegen？

因为量化改变了 dtype、scale/zero-point 处理和后端可用 kernel。原先的浮点融合模式不一定直接适用，往往要针对量化算子重新选择 pattern 和 lowering 路径。

实践步骤：

1. 找一个线性层或卷积权重张量，做简单 min-max 量化。
2. 比较 `per-tensor` 和 `per-channel` 的误差。
3. 在一个小图上统计中间张量生命周期。
4. 尝试手工做一次 buffer 复用规划。

## 9. Runtime、系统与性能分析

### 61. 编译器和 runtime 的职责边界怎么分？

编译器负责图变换、代码生成、调度决策和静态信息准备；runtime 负责真正执行、内存分配、kernel 调度、设备管理、异步同步和错误处理。好的系统会让两者信息传递清晰，而不是职责混乱。

### 62. 为什么 AI 编译器往往离不开 runtime？

因为很多信息只有运行时才知道，例如真实输入 shape、动态 batch、设备状态、stream、内存池状态等。尤其动态 shape 和多后端系统，没有 runtime 很难闭环。

### 63. 静态 shape 和动态 shape 的主要差异是什么？

静态 shape 更容易做激进优化和内存规划；动态 shape 更灵活，但需要 guard、shape function、runtime dispatch 或多版本代码。现代框架常采用“专门化 + fallback”的策略。

### 64. autotuning 是什么？

autotuning 是自动搜索 kernel 配置或调度参数，例如 tile 大小、线程布局、pipeline depth。它常用于 GEMM、卷积、attention 这种性能高度依赖参数组合的算子。

### 65. benchmark 时为什么要做 warmup？

warmup 可以避开首次编译、缓存填充、lazy init、显存分配和频率爬升带来的噪声。没有 warmup 的首轮结果通常不稳定，也不能代表 steady state。

### 66. 如何判断一个 kernel 是算力瓶颈还是带宽瓶颈？

可以结合 roofline 思路：看算术强度、理论峰值、实际 FLOPS 和带宽利用率。若带宽接近上限而 FLOPS 不高，多半是带宽瓶颈；反之则可能是算力或流水线瓶颈。

### 67. profiler 常看哪些指标？

常看 kernel 时间、launch 次数、SM 利用率、occupancy、global load/store throughput、L2 hit、shared memory conflict、寄存器使用、stall 原因、内存拷贝时间。

### 68. 为什么“小优化 benchmark 有提升，上线却没效果”？

可能因为测试数据不代表真实 workload，或者优化只改善了局部热点却没有改变端到端关键路径。也可能上线受制于调度、I/O、batch 变化、异步等待、其他服务开销。

### 69. 动态 shape 编译常见做法有哪些？

常见做法有 shape polymorphism、symbolic shape、shape specialization、guard + cache、多版本 kernel 和 runtime fallback。不同系统在编译开销和泛化能力之间做权衡。

### 70. 什么是 correctness check？

correctness check 就是验证优化前后语义一致，通常包括数值误差比较、随机输入对拍、边界 case、不同 dtype 校验、与 reference backend 对比。没有严谨对拍的性能优化很危险。

实践步骤：

1. 为一个小 kernel 写 benchmark 脚本。
2. 加入 warmup、重复测量、均值与 P95 统计。
3. 用 profiler 收集至少 3 个关键指标。
4. 给优化前后结果做 correctness 对拍。

## 10. 项目设计与落地题

### 71. 如果让你设计一个教学型 AI 编译器，最小闭环应该包含什么？

至少包含前端导入、一个简单 IR、几个基础优化 pass、一个 reference backend、若干样例和测试。最小闭环的重点不是功能多，而是“从模型到结果”能跑通并可观察。

### 72. 你的 IR 为什么要用 `Node + Value` 模型？

因为这能清楚表达“操作”和“数据边”的区别，def-use 关系也比较自然。对教学型图编译器来说，可读性和易于做遍历、替换、DCE 很重要。

### 73. 为什么 pass manager 要独立出来？

pass manager 可以统一组织 pass 顺序、日志、开关、统计和失败处理。没有它，优化流程很快会散落在各个脚本和函数里，难以维护和复现。

### 74. 什么时候应该优先做 reference backend？

在你还没有稳定后端之前，reference backend 是验证 IR 语义、优化正确性和单测的基准。它往往用最朴素的 CPU/Numpy 实现，但价值非常高。

### 75. 如何设计一个融合 pass？

先明确定义 pattern、合法性条件和收益模型，再决定如何替换图结构并保持输出等价。最后要配套 dump、对拍和 benchmark，否则很难证明 pass 真的可靠。

### 76. 如何设计前端导入层？

前端导入层最好只做“语义保持”的映射，不要过早混入复杂优化。它应尽量保留源码图信息、shape、dtype、常量和位置信息，便于后续 pass 使用。

### 77. 如何设计编译日志和调试能力？

至少要能 dump 原始图、每轮 pass 前后 IR、统计变换数量和失败原因。若能支持按 pass 单独开关、最小复现输入和差异对比，调试效率会高很多。

### 78. 如何逐步从 Python 原型走向 MLIR 正式实现？

先把 Python 原型的 IR 语义、pass 和验证方法稳定下来，再把高价值部分映射到 MLIR dialect/pass。迁移时应保留一套 reference 测试，避免“重写后看似更正规，但功能退化”。

### 79. 为什么很多 AI 编译器项目都强调 benchmark 入口？

因为没有 benchmark 很难判断优化的实际价值，也无法定位收益来自哪里。面试里如果你能展示“优化前后速度、峰值内存、误差”而不只是“我实现了某 pass”，说服力会高很多。

### 80. 如果目标后端是自研 NPU，编译器要额外考虑什么？

要考虑算子支持集、特殊 layout、地址空间、DMA、片上 SRAM、静态调度、量化格式、核间同步和 runtime 协议。很多时候真正难点不是 IR，而是把硬件约束准确编码进编译流程。

实践步骤：

1. 选一个最小模型，例如两层 MLP。
2. 写前端导入，把模型映射成自定义图 IR。
3. 实现 `constant fold`、`dce`、一个简单融合 pass。
4. 写 CPU reference backend 和对拍测试。
5. 加一个 benchmark 入口，记录优化前后差异。

## 11. 算法与手写题

### 81. 为什么 AI 编译器岗位还会考算法题？

因为这类岗位虽然偏系统，但仍需要考察基础编码能力、数据结构意识和边界处理能力。很多团队的手撕难度不会特别高，但会看代码风格和调试思路。

### 82. LRU 缓存怎么实现？

标准做法是 `unordered_map + doubly linked list`。哈希表负责 `O(1)` 定位节点，双链表维护最近使用顺序，头部最近用、尾部最久未用。

### 83. 为什么 LRU 通常不用单链表？

因为要在 `O(1)` 时间删除任意已知节点，单链表删除需要前驱节点，不方便。双链表配合迭代器或节点指针更合适。

### 84. 拓扑排序有什么用？

图编译里常用它来保证节点按依赖顺序处理，例如 shape inference、代码生成、执行计划和某些图优化。常见实现是 Kahn 算法或 DFS 后序。

### 85. 并查集在什么场景有用？

适合处理连通性、等价类合并、设备分组或某些图归并问题。虽然不是 AI 编译器最常用结构，但面试常把它当基础题考察。

### 86. 为什么树和图遍历在面试里常出现？

很多编译器分析本质上就是在图上做遍历，例如 def-use 图、支配树、调用图、计算图。面试官会借简单图题看你是否具备迁移到真实 IR 的能力。

### 87. 如何判断一棵树是否是合法 BST？

常用方法是中序遍历检查是否严格递增，或者递归维护上下界。实现时要注意边界值，不能直接把 `INT_MIN` 当作哨兵而不做额外处理。

### 88. 二叉树最近公共祖先怎么做？

普通二叉树常用递归：若当前节点为空或命中 `p/q` 就返回；递归查左右子树，若左右都非空则当前节点是 LCA，否则返回非空一侧。

### 89. 为什么链表题常考快慢指针？

快慢指针能在 `O(1)` 额外空间里完成中点查找、环检测、区间反转切分等操作。它反映的是你对指针移动不变量的理解。

### 90. 手写题答得一般时，怎么尽量减少失分？

先讲清思路、复杂度和边界条件，再写结构清晰的代码。若时间不够，至少保证基本版本正确、命名清楚，并主动说明还能如何优化。

实践步骤：

1. 手写一次 `LRUCache`。
2. 再手写一次拓扑排序和并查集。
3. 每道题都补 3 组边界 case。
4. 练习口述复杂度和错误点，而不只是把代码写出来。

## 12. 项目深挖与行为面

### 91. 面试官为什么特别喜欢顺着项目深挖？

因为项目最能区分“真的做过”还是“只会背概念”。尤其 AI 编译器岗位，很多候选人能讲 MLIR/Triton 名词，但一追问细节就露馅。

### 92. 项目介绍应该怎么开场？

建议用“目标、输入、IR、核心 pass、后端、验证结果”六个点快速讲清楚。让面试官先建立全局图，再自然进入细节。

### 93. 被问“你这个优化为什么有效”时应该怎么答？

要从原始瓶颈、优化动作、理论收益和实测结果四个维度回答。不要只说“减少了算子数量”，最好说明减少了哪些内存访问、launch 或冗余计算。

### 94. 被问“为什么不用现成框架”时怎么答？

可以从教学目的、可控性、验证某个想法、复现特定 pipeline、探索自定义硬件适配等角度回答。关键是说明你的项目目标不是“重复造轮子”，而是为某个学习或研发目标服务。

### 95. 项目里遇到过最难的 bug 是什么，怎么排的？

高质量回答应覆盖现象、定位方法、最终根因、修复方案和预防措施。编译器项目里常见难 bug 包括 shape 推导错、重写后 use-def 关系损坏、量化尺度错、异步执行竞态等。

### 96. 如何证明你写的 pass 没把语义改坏？

要讲 reference backend、随机输入对拍、单测、IR 断言、优化前后输出误差和回归 benchmark。只有“看起来能跑”远远不够。

### 97. 如果项目性能提升不明显，面试里怎么讲？

实话实说，然后强调你如何定位瓶颈、发现当前优化不是主因、下一步准备怎样改。很多时候诚实的分析比“硬说自己优化了很多”更加分。

### 98. 被问“你的项目如果继续做，下一步是什么”时怎么答？

最好结合现有架构说清演进路线，例如“先稳定 Python 原型，再迁移高价值 pass 到 MLIR，再做 LLVM/Triton 后端闭环”。这样能体现你有系统规划而不是想到哪做到哪。

### 99. 行为面里怎么体现协作能力？

可以讲你如何和模型、系统、硬件同学对齐接口，如何复现实验，如何写文档和 benchmark，如何处理需求变更。AI 编译器岗位常跨多个团队，协作表达很重要。

### 100. 如果被问“为什么想做 AI 编译器”，怎么答更有说服力？

比较好的回答通常会连接三个点：你对编译器抽象和性能优化的兴趣、你对 AI 系统真实瓶颈的观察、以及你已经动手做过相关项目。把“兴趣”落到“长期投入证据”上，会比空泛表态更有说服力。

实践步骤：

1. 给自己的一个项目写 2 分钟和 5 分钟两个版本的介绍。
2. 分别准备“技术亮点”“困难问题”“收益数据”“后续规划”四张提纲卡片。
3. 找同学或自己录音，连续追问 10 分钟，检查有没有答非所问或细节断层。

## 13. 推荐复习顺序

如果你当前目标是国内 AI 编译器岗位，建议按下面顺序准备：

1. 先补 `C++`、数据结构、编译基础。
2. 再补 `MLIR / LLVM` 和 `CUDA / Triton` 两条主线。
3. 然后把“图优化、量化、内存规划、runtime”串成一条完整链路。
4. 最后回到自己的项目，把每个模块落到一个真实实现或实验上。

## 14. 推荐实践清单

为了把这 100 题从“会背”变成“会答”，建议至少做完下面 8 个实践：

1. 手写一个 `LRUCache`
2. 手写一个最小图 IR
3. 实现 `constant folding + dce + simple fusion`
