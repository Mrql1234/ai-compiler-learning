# 问题解答：量化与推理框架

## 1. 为什么 per-channel weight quantization 比 per-tensor 更稳

核心原因是：**不同输出通道的权重分布通常差异很大**。

如果使用 per-tensor quantization，整个权重张量只能共享一个 `scale`。这会带来两个问题：

1. 某些数值范围很大的通道会主导全局 `scale`
2. 数值范围较小的通道会被迫使用过粗的量化粒度

结果就是：

- 大通道能勉强表示
- 小通道的有效精度损失更明显
- 整体误差更容易集中到某些输出通道上

per-channel weight quantization 的做法是：**每个输出通道单独拥有自己的 `scale`**。这样每个通道都按自己的动态范围量化，误差通常更均匀，也更小。

对 `linear` 或 `conv` 来说，这通常更稳，因为：

- 每个输出通道本来就对应一组独立权重
- 每个通道承担的特征提取角色可能不同
- 通道间权重幅值差异是很常见的

所以在部署实践里，权重量化经常优先选择 per-channel，而不是 per-tensor。

## 2. 为什么量化只解决“表示和带宽”问题，不解决 runtime 调度问题

量化主要解决的是**单个算子或单个模型副本的表示成本**：

- 参数更小
- 激活更小
- 显存 / 内存占用更低
- 带宽压力更低
- 某些硬件上低精度算子吞吐更高

但 runtime 调度关心的是另一类问题：

- 多个请求如何排队
- 哪些请求一起 batch
- KV-cache 如何分配和回收
- prompt 阶段和 decode 阶段怎么争资源
- 如何在延迟和吞吐之间做权衡

量化不会自动回答这些问题。

举个例子：

- 量化可以让每个请求占用的 KV 或权重内存更少
- 但“先服务谁”“何时合批”“页不够时谁等待”这些决策，仍然要由 scheduler 决定

所以量化提高的是**单请求资源效率**，而 runtime 调度决定的是**多请求系统效率**。两者相关，但不是同一个层面的问题。

## 3. 为什么 vLLM / TensorRT-LLM 这类系统的关键在 KV cache 和 batching，而不只是 kernel 快

因为 LLM 推理的瓶颈，很多时候并不只在单个 kernel 的算力，而在**系统如何持续喂饱 GPU**。

### KV cache 重要的原因

自回归生成时，每生成一个 token，都要反复使用之前 token 的 K/V。

如果 KV cache 管理不好，会出现：

- 显存浪费
- 碎片化
- 可并发请求数下降
- 长上下文时更容易 OOM

vLLM 的 PagedAttention 本质上就是在解决：

- KV 如何分页管理
- 如何减少连续大块内存需求
- 如何提升显存利用率和请求承载量

### batching 重要的原因

单个请求往往不足以把 GPU 吃满，尤其在 decode 阶段更明显，因为每步只生成很少 token。

如果没有好的 batching：

- GPU 会频繁空转
- 吞吐很低
- 系统整体成本很高

continuous batching 的意义在于：

- 新请求可以不断插入
- 已在运行的请求可以继续共享 batch
- 系统不必等一个固定 batch 完整结束才开始下一批

这样做通常会显著提升吞吐，并改善资源利用率。

### 为什么“kernel 快”还不够

即使某个 kernel 非常快，如果：

- KV 管理很差
- batch 组织很差
- 请求调度很差

那么 GPU 仍可能大部分时间在等待，或者只能跑很低并发。

所以：

- TensorRT-LLM 更偏向把 kernel、图优化、低精度执行做到极致
- vLLM 更突出 runtime 层面对请求和 KV 的组织能力

两者真正解决的是不同层次的问题，但共同点是：**系统级吞吐和延迟，取决于内存管理与调度策略，不只是单 kernel 峰值性能。**

## 4. 这个项目是否需要在 GPU 云服务器上运行

当前这个项目**不需要**。

现在的 `Quant Inference Lab` 主要是：

- 量化数值实验
- INT8 reference 路径
- KV-cache 和 scheduler 模拟

这些内容都可以在 CPU 上完成，而且用 CPU 更方便聚焦原理。

你只有在下面这些扩展阶段，才建议切到 GPU 云服务器：

1. 想接入真实 vLLM / TensorRT-LLM
2. 想测真实量化模型吞吐和延迟
3. 想做 CUDA / Triton kernel 优化
4. 想做更接近生产的高并发推理实验
